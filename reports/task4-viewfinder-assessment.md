## 1. 每帧链路与瓶颈定位

```
OV3640 DVP 640×480 UYVY（合并读出）
  → mosaico_camera_get_frame（等帧，受传感器帧率限制）            [相机任务，核 0]
  → film_viewfinder_convert：裁切 + 逆时针 90° + UYVY→RGB565   [同一任务，核 0]
  → publish_slot（三槽环，界面没取走就丢帧）
  → 界面 shell_tick（16 ms 一次）→ film_app_step → 有新帧才重画 [GSP 任务，核 1]
  → film_app_render 只重画取景框（damage rect）+ 覆盖层
  → esp_gsp_canvas_invalidate_dirty 只送这块到屏幕
```

已有的优化（评估前就在代码里，不是新增）：
- **脏矩形**：`film_shell.c: shell_render` 只重画 `film_app_damage()`；GSP 只送该矩形。取景期间不重绘整屏。
- **转换已是缓存友好的**：按 16 行一组处理，每组每列只读传感器一行里相邻的几十字节，写入的 16 行取景缓冲留在 L1；RGB565 查表（5 KB，放 DRAM）一次完成截断、截位、移位，没有逐像素分支。
- **不用 PPA/2D-DMA**：代码注释记录了"显示刷新要用 2D-DMA，取景再用 PPA 抢 2D-DMA 时整个队列曾被卡死"。

每段预算（待实机，填表用）：

| 段 | 估算依据 | 实测（待实机） |
|---|---|---|
| 传感器帧率上限 | `camera ready: WxH @N fps` 日志 | `perf vf` capture_wait |
| 转换 | 480×360=172.8k 像素 × 每像素 3 次字节读 + 4 次乘法 + 3 次查表 + 1 次写；估计 15–30 ms/帧（PSRAM 源帧读取占大头） | `perf vf` convert |
| 界面取走延迟 | 界面最多 16 ms 才轮询一次；`pick_write_slot` 在上一帧没被取走时直接丢帧 | `perf vf` ui_pickup_latency / dropped_no_slot |
| 重画取景框 | 480×360 的 gfx 拷贝 + 覆盖层（电池、水平仪、日期戳）| `film_shell` stats 的 avg_us/commit_avg_us |

判断：帧率上限 = min(传感器帧率, 1/转换时间, 界面取走频率)。如果设备上"非常慢"是用户的原话，最可能的原因是**转换时间 + 帧丢弃**（转换在核 0，与相机任务同核，且帧源在 PSRAM），而不是显示刷新（只送脏矩形）。**这一点必须用实机数据确认**，不能凭估算选方案。

## 2. 优化选项逐项评估

| 选项 | 预期收益 | 代价/风险 | 决定 |
|---|---|---|---|
| UI 覆盖层脏矩形/分层 | — | **已具备**（见上） | 无需新增 |
| 转换内循环：色度项查表替换乘法 | 每像素省 4 次乘法（换 4 次 DRAM 表读取）；收益取决于核的乘法延迟和表读命中 | 与现实现逐位一致，host test 可验；实机 A/B 前不能确认一定更快 | **实现**，保留旧路径作为对照（Kconfig 或编译期开关），实测后取优 |
| 转换：32/64 位批量处理 | 源是跨行读，目标是 16 行转置写，位宽加大基本不起作用 | 复杂、易错 | 不做 |
| 转换：内部 RAM 放置 | 表已在 DRAM；帧缓冲（PSRAM）放不进内部 RAM | — | 已最优 |
| PPA/2D-DMA 做旋转+色彩转换 | 理论上把 CPU 转换降到近 0 | 旧版出现过 2D-DMA 队列卡死；需要在实机上与显示刷新错峰验证，**不能在没有设备数据时重新打开** | 暂缓，列为"实测后评估"，不在本轮改动 |
| 传感器输出更接近目标尺寸的窗口 | 640×480 → 取景窗约 360 高，传感器侧缩小到 480×360 可少读 44% 像素 | 需要修改 `mosaico_module_camera` 的窗口/缩放配置（BSP 子模块，且与拍照格式切换耦合） | 本轮不改 BSP；列入风险与后续项 |
| 三级流水线并行 | 现在采集（DMA）与转换已并行（驱动多缓冲）；转换与界面通过三槽环解耦；没有多余拷贝 | — | 已具备 |
| 帧丢弃策略 | 上一帧没被取走就丢帧是对的（避免白占 CPU）；但取走延迟≥16 ms 会降低可见帧率 | 把 `SHELL_TICK_MS` 取景页降到 8–10 ms 可减少取走延迟，代价是空闲轮询增多 | 先实机看 ui_pickup_latency，再定；本轮不改 |

## 3. "胶片取景"（取景叠加胶卷色调）

设计：**不增加每像素的运算次数**，只换查表的内容。
- 现在转换的 RGB565 表以"BT.601 结果 + 偏移"为下标，一次查表同时完成截断。让这三张表直接带上胶卷的色调曲线：下标是原始通道值，输出是曲线后的 565 位。每像素仍是 3 次查表，**帧率代价约 0**。
- 饱和度：对色度项 (u−128, v−128) 乘 Q8 系数，每像素 2 次乘法（只有胶卷启用时）。
- 黑白：只用 Y，查同一张曲线表，写 R=G=B（比彩色更省）。
- 暗部/高光色调：按输入值线性混合折进每通道曲线（近似，取景用）。
- 不做：颗粒、光晕、漏光、暗角、像素风（取景保持原样）。
- LUT 由 `film_filter` 的胶卷预设直接生成（`film_filter_viewfinder_look()`），任务 5 的新胶片只要有预设就自动有取景 LUT；需要原语（局部对比、色相映射等）的胶片只近似其曲线/饱和/单色部分。
- 开关：设置项"胶片取景"（默认关）。曝光补偿 EV 在曲线之前，取景表随 EV 重新生成（生成一次 3×256 项，几十微秒）。
- 代价评估：**待实机**，预期与关闭时帧率相同；如果实测有差异再决定默认值。

## 4. 验收对应

- ≥25 fps、冻结延迟 <50 ms：**待实机**；冻结延迟（快门按下 → 画面冻结）取决于界面下一次 tick 与 `SHOT_FLASH` 的处理，代码上是同一次 `cam_fire` 里把当前取景帧复制到 `cam->frozen`，没有等待，估计 ≤1 个界面周期（16–32 ms），在帧时间线日志里确认。
- 优化前后的分段对比表：由 `perf vf` 日志在优化前后各取一份，最终报告里填。
- 任务 3 的后台冲洗场景下复测：任务 3 采用"延后 + 可抢占"，取景与全尺寸冲洗不同时运行，所以"冲洗期间取景帧率"测的是"连拍/小样/写盘期间"。
