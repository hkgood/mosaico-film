# 任务 3 评估：拍冲解耦

状态：评估完成，结论为**可行，但按"延后 + 可抢占"实现，而不是"取景与冲洗同时跑"**（见 §3）。
带"待实机"的数字是读代码得出的估算，不是实测；实测由阶段 0 的 `CONFIG_FILM_PERF_TRACE` 在一次批量上机里采集。

## 1. 基线：现在的快门间隔由什么组成

代码路径（`dev_shoot` → `film_camera_capture` → `capture()` → `film_lab_deliver_still` → `run_job`）：

| 段 | 做什么 | 来源 | 占用取景？ |
|---|---|---|---|
| A 停取景 | `grab_proof` 取最后一帧小样源，`stream_stop` | `film_camera.c: capture` | 是 |
| B 切格式 | `film_still_open`：切 JPEG 2048×1536、搬曝光、锁白平衡 | `film_still.c` | 是 |
| C 等有效帧 | 丢掉空帧/坏帧，取第 2 张有效帧（日志里见过前两帧被拒） | `STILL_TAKE_VALID_FRAME` | 是 |
| D 恢复 | `still_close` 切回取景格式 | `film_still.c` | 是 |
| E 小样 | 屏幕尺寸冲洗，约 0.5 s | `develop_proof` | 取景被 `hold` |
| F 全尺寸冲洗 | 解码 + 滤镜 + 编码，数秒 | `run_job` | 取景被 `hold` |
| G 写盘 | RAW/JPG/SCR/THM，约 0.1–0.28 MB/s | `film_writer` | 否（后台） |

关键事实：
- `film_camera_capture` 把 `hold` 置为 true（"拍完后取景保持暂停，等暗房冲洗完再恢复"），`on_lab_busy(false)` 才放开。所以**快门间隔 = A+B+C+D+E+F + 取景重新开流**，其中 E+F 占大头，且 `film_lab_reserve` 在整个期间返回忙。
- UI 侧：M6 的 `SHOT_REVEAL → SHOT_FLY` 要等 `PROGRESS_DONE`，再加固定动画（70+260+520+1100+380 ms ≈ 2.3 s）才回到 `SHOT_IDLE`，`cam_fire` 才再次放行。即使暗房不忙，UI 自己也卡住约 2.3 s。
- 全分辨率（任务 1）把 F 拉得更长（软件解码 3.1 MP + 约 2× 滤镜像素），所以不解耦的话快门间隔会比旧版更差。
- A–D 的时间基线：**待实机**（`perf shot` 会按"停取景 / 切格式 / 曝光帧到达"三段打印）。

## 2. 方案

拍摄只做"取到原片并落盘"，冲洗挪到后面：

```
快门 → [A B C D] 原片 JPEG → 拼 EXIF → 写 RAW 到 NAND（写盘任务）→ 写 .PND 续冲标记
          │                      └ 同时：小样（屏幕尺寸，不停取景）→ UI 看到成片预览
          └ 取景立刻恢复
后台：安静 ≥ QUIET 之后，暗房按顺序"从 RAW 文件冲洗"（与重新冲洗同一条路径），
      冲完写 JPG/SCR/THM → commit → 删 .PND
```

要点：
1. **原片只有一份内存拷贝**：带 EXIF 的 RAW blob 交给写盘任务，写完即释放；之后冲洗从 NAND 读回（重新冲洗已经是这条路径，读比写快一个数量级）。每个待冲洗的照片，内存里只在"RAW 还没写完"的几秒占 0.6–0.75 MB。
2. **队列深度 N = 3**：`film_lab_reserve` 改为"正在取景拍摄、或待冲洗数 ≥ N 才拒绝"。N=3 时最坏内存 ≈ 3 × 0.75 = 2.2 MB（RAW 还没写完的 blob）。UI 在计数窗显示待冲洗张数。
3. **小样照旧即时出**：`develop_proof` 只用屏幕尺寸缓冲，不需要停取景；小样的通道均值 `proof_stats` 与白平衡增益 `awb` 留在待冲洗记录里，全尺寸冲洗时沿用（断电后丢失，续冲时由暗房独立估算，只影响色彩校正的细微匹配）。
4. **延后策略**：距离最近一次快门/取景拍摄不到 `LAB_QUIET_MS`（建议 2.5 s）时不开始全尺寸冲洗。连拍期间取景 100% 跑；停手后才冲。
5. **可抢占**：冲洗中按快门 → `film_lab_reserve` 置 `abort`，解码阶段（占 ~78% 时间）在每个条带检查，立即放弃本张（RAW 已落盘，下次从头冲）；放弃后恢复取景再拍。滤镜之后不再抢占（已接近完成，剩余 <20%）。
6. **UI**：M6 的 `SHOT_REVEAL` 不再等 `PROGRESS_DONE`，小样停留够时间就飞入；在 HOLD/REVEAL/FLY 期间按快门，直接结束上一张动画再拍（快门间隔不再被 2.3 s 动画卡住）。

## 3. 资源争用分析

**核与优先级**（`film_port_dev.c`）：

| 核 0 | 核 1 |
|---|---|
| 相机任务 prio 5（取景转换、拍照） | GSP 渲染（固定核 1） |
| 暗房任务 prio 3 | 分享任务 prio 4 |
| 电源/显示任务 prio 6（醒来即睡） | 滤镜并行 worker（`film_filter parallel`，落在另一核） |
| 写盘任务 prio 2（不绑核） | |

取景时核 0 被相机占满；全尺寸冲洗时暗房占核 0、滤镜 worker 占核 1，GSP 渲染在核 1 与 worker 抢。

**内存（PSRAM）**：冲洗开始时空闲约 7.3 MB（取景已停）。YUV420 存放 M6 约 4.7 MB、SX-70 约 5.4 MB，加解码器输出缓冲、编码输出缓冲（0.4 B/px）、原片，峰值估算 M6 ≈ 6.3–6.9 MB、SX-70 ≈ 7.1–7.9 MB（**待实机，`job PSRAM peak` 日志会给出**）。取景三缓冲 1.04 MB 加驱动帧缓冲必须释放才放得下。

**结论：全尺寸冲洗无法与取景同时运行。**
- 内存：SX-70 的峰值已逼近全部空闲 PSRAM，取景缓冲放不进去。
- CPU：解码在核 0（与相机任务同核），滤镜 worker 在核 1（与 GSP 同核）；两颗核都被占满，取景帧率与 UI 流畅度都会明显下降，不可能稳定在基线 70% 以上。
- 任务要求的"后台冲洗期间取景帧率不低于基线 70%"因此**按字面不可达**。我把要求的意图（"连拍时取景不被冲洗拖慢；冲洗不挡住下一张"）用"延后 + 可抢占"满足：
  - 拍摄/连拍期间：取景 = 基线（没有冲洗在跑，仅有小样 ≈ 0.5 s 的屏幕尺寸计算与后台写盘）；
  - 停手后：取景暂停，冲洗期间是"显影中"状态，按快门立即抢占（目标 <1 s 回到取景可拍）。
- 取景与小样/写盘同时运行的影响（小样 0.5 s 一次、写盘 NAND 带宽）：**待实机**，记录取景 fps 跌幅。

## 4. 加速冲洗选项

| 选项 | 评估 | 结论 |
|---|---|---|
| (a) BSP `mosaico_module_camera` 的硬件 JPEG 解码 | 硬件解码需整幅输出，3.1 MP RGB/YUV 缓冲与现有内存预算冲突；且解码输出格式要与条带管线匹配。需要先在实机验证能否输出 YUV420 并按行读取。 | 不在本轮采用；列为后续优化（若实机证明软件解码是瓶颈，价值最大） |
| (b) 只解码需要的区域/MCU 行 | M6 全画幅 1:1 输出用到全部像素，没有可省的；4:3 裁切省 25%，已按条带只解码需要的行。 | 已具备，无额外收益 |
| (c) 降低滤镜并行度，留一核给取景 | 取景与冲洗不同时运行，无意义；但"冲洗时界面（GSP）仍流畅"可受益。 | 保持 parallel，不改 |
| (d) 每条带 yield | 抢占检查点本来就放在条带边界，顺手 `taskYIELD`，代价极小，让 UI/写盘调度更顺。 | 采用 |

推荐组合：延后 + 条带检查点抢占（d）。（a）视实机数据决定。

## 5. 无法避免的部分（A–D）

- 取景（640×480 合并读出）与拍照（2048×1536 JPEG）是不同的传感器格式，每次快门都要停流、切格式、搬运曝光与白平衡、等有效帧、切回。
- 可缩短的点（**待实机验证**，均不改传感器驱动）：
  1. `STILL_TAKE_VALID_FRAME` 取第 2 张有效帧是因为第 1 张偏暗；如果曝光搬运足够准，改取第 1 张可省一帧时间（约 1/帧率）。需要对比两种曝光，色彩观感由用户确认，所以本轮**不改**。
  2. `grab_proof` 与 `stream_stop` 之间没有额外等待，已经最短。
  3. 避免完整 close/open：V4L2 流关闭/重开是驱动级操作，复用缓冲需要改 `esp_video`，超出范围。
- 因此快门间隔的下限由 A–D 决定。拿到实测数据后：若 A–D ≤ 0.8 s，则"≤1 s 间隔"可达；若 >1 s，需要用 1. 项或驱动改造才能达到，这是**最大的未决风险**，会在最终报告里给出实测。

## 6. 可靠性（断电续冲、休眠、低电量）

- **落盘顺序**：RAW 先写（带 EXIF，已有逻辑）→ 写完才写 `.PND`（约 100 字节：版本 + `film_shot_t` 关键字段 + CRC）。`.PND` 存在 = RAW 完整。
- **开机续冲**：存储挂载后，暗房在空闲时扫描 `.PND`，校验 CRC 与 RAW（以 EOI 结尾），合格的按"重新冲洗到自己"入队（`source_id == photo_id`，不复制 RAW，不改编号）；`_RAW.JPG` 没有 `.PND` 也没有 `.SCR` 的是写了一半的孤儿，删除。冲洗 commit 成功后删 `.PND`。
- **编号**：相册 `next_id` 之前只看 `.SCR`。续冲的照片还没有 `.SCR`，必须让 `film_library` 扫描时也把 `.PND` / `_RAW.JPG` 的编号算进去，否则重启后会给新照片发重复编号。
- **写盘期间断电**：RAW 还在写 → 这张照片丢失（不可避免，NAND 写入每张约 3–7 s）。UI 在快门后的"保存中"期间提示请勿断电。
- **休眠**：`dev_keep_awake` 已经在冲洗/写盘期间阻止调暗；待冲洗队列非空时同样返回 true，直到全部落盘。
- **低电量**：电量低于阈值时（沿用电源任务读数）不再启动新的全尺寸冲洗，只保证 RAW + `.PND` 落盘；下次开机续冲。

## 7. 实现计划（按风险从低到高）

1. `film_library`：编号扫描包含 `.PND` / `_RAW.JPG`（host test）。
2. `.PND` 编解码与校验（可移植、host test：往返、CRC 损坏、截断）。
3. `film_writer`：独立的"RAW 小事务"（RAW + `.PND`，不与 JPG 的 commit 共享 `photo_err`）；成功 commit 后删 `.PND`。
4. `film_lab`：待冲洗队列、延后策略、抢占、`reserve` 语义、开机续冲。
5. `film_camera`：快门后不再强制 `hold`。
6. UI：待冲洗张数、M6 动画不再等冲洗、动画期间可按快门（host UI 测试覆盖）。

验收项（连拍 5 次间隔 ≤1 s、断电续冲）只能实机验证，列入最终清单。
